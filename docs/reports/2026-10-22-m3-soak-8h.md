## 3. 现象分析与后续定位

### 3.1 上屏帧率 51 fps 的根因

本轮测试中服务端编码与客户端解码均为 59.9 fps，但客户端实际呈现帧率为 51.0 fps（约 15% 的帧在渲染层被合并）。

经过次日对照实验（见 [present 同步修复](2026-10-22-present-sync-fix.md)），确认根因为当时客户端设置了 `CAMetalLayer.displaySyncEnabled = false`，导致 macOS 合成器丢弃/合并了约 15% 的提交帧。将 `displaySyncEnabled` 恢复为开启（默认 `true`）后，客户端呈现帧率立即恢复至 **59.5–60.0 fps**。

### 3.2 高码率下的排队延迟

本轮全屏动态画面码率达 1,190 Mbps（每帧约 2.48 MB），`capture→present` P95 为 48.4 ms；而在 42 Mbps 低码率对照下 P95 为 30.5 ms：

| 条件 | 源分辨率 | 码率 | 呈现 fps | P50 | P95 |
|---|---|---|---|---|---|
| 8h 长稳（高动态） | 4K | 1,190 Mbps | 51.0 | 40.2 ms | 48.4 ms |
| 测试图 + `--input` | 4K | 42 Mbps | 51.4 | 22.6 ms | 30.5 ms |
| 测试图，无 `--input` | 4K | 42 Mbps | 51.1 | 26.0 ms | 33.8 ms |
| 测试图 + `--input` | 1080p | 11.8 Mbps | 51.3 | 28.2 ms | 35.9 ms |

数据表明 `--input` 事件捕获对渲染延迟无负面影响；高码率下延迟上升主要来自大帧传输与显示链路等待（后续在 B7 中通过到帧即时泵送 `view.draw()` 消除了约 8 ms 的显示链路等待）。

### 3.3 偶发单帧抖动

8 小时内仅出现 7 次单帧延迟超过 80 ms 的瞬态抖动（最大一次为 21:33 的 431 ms），所在窗口仍正常渲染 3042 帧，无累积趋势。

## 4. 运行前置检查项（已固化至 `scripts/soak-preflight.sh`）

1. **使用字面 IP 连接**：本机代理可能将主机名劫持为 fake-ip 段地址导致连接被重置；
2. **GUI 责任进程授权**：ScreenCaptureKit 屏幕录制权限绑定在 GUI 责任进程名下，不能直接从裸 SSH 会话启动服务端；
3. **防止显示器休眠**：显示器休眠会导致 `SCStream` 停止出帧，服务端已内建 `PreventUserIdleDisplaySleep` 断言，长跑前亦可配合 `caffeinate -disu`；
4. **清理残留服务端进程**：启动前确认无旧的 `boltkvm server` 进程残留。
