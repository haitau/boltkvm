# M0 前置验证报告：3008×1692 HiDPI 虚拟显示与捕获面

- 日期：2026-10-21
- 范围：显示层与雷雳链路基线；不涉及视频编解码、输入、音频与端到端延迟
- 结论：**显示层通过**。无头被控端可稳定提供 `3008×1692 HiDPI @ 60Hz` 虚拟显示，ScreenCaptureKit 可按 `6016×3384` 原生背板尺寸采集。M0 的无头拔线、睡眠/重启、音频可听性、本地延迟基准与 A′ 排除项仍待人工亲验。

## 1. 环境

| 项 | 实测 |
|---|---|
| 主控端 | Apple M5 Pro，macOS 27.0.1，外接 T3252U：背板 `6016×3384` / UI `3008×1692 @ 60Hz` |
| 被控端 | Apple M4 Pro，macOS 27.0.1，开发期间临时接 UGREEN `2560×1440 @ 30Hz` |
| 连接 | Thunderbolt Bridge，`bridge0` 独立子网，控制器 `<bridge-ip-controller>`，被控端 `<bridge-ip-mini>` |
| 虚拟显示工具 | vdscreen 1.3.4（Homebrew cask，`/Applications/VDScreenBar.app`） |
| 被控端会话 | 已登录 Aqua 会话；FileVault 关闭，自动登录开启（用户名略） |

> 公开仓不记录真实主机名、SSH 别名、用户名与内网地址；下文统一用占位符。

## 2. 虚拟显示

### 2.1 安装

```bash
ssh <mini> 'eval "$(/opt/homebrew/bin/brew shellenv)" && \
  brew tap lyonDan/tap && brew install --cask lyonDan/tap/vdscreen'
```

### 2.2 创建 3008×1692 HiDPI

```bash

```

原始输出【事实】：

```text
已就绪："iPad mini 7"  displayID=11  UI 3008x1692  背板 6016x3384  HiDPI
身份：serial=949597171 uuid=5E20E52D-9E1C-4020-AA60-00208E45FCD5
  实际: 背板 6016x3384 / 逻辑 3008x1692 —— HiDPI
```

`system_profiler SPDisplaysDataType`【事实】：

说明：首次创建沿用 vdscreen 预设名 `iPad mini 7`，随后改名 `BoltKVM`；尺寸与模式不变。最终配置：

### 2.3 稳定性与可逆性

| 检查 | 结果 |
|---|---|
| 连续运行 | 进程启动 `11:12:19`，检查时 `11:22:37`，`etime=10:18`，显示仍在 | 【事实】通过 |
| `vdscreen off` | 输出 `已关闭（是否开机自启：否）`，`vdscreen state` 为 `off`，显示列表只剩 UGREEN | 【事实】通过 |
| 再次 `vdscreen on 3008x1692` | 新 `displayID=12`，仍为 `UI 3008×1692 / 背板 6016×3384 HiDPI` | 【事实】通过 |
| `launchctl kickstart -k` | 核心进程被强制重启后显示恢复 | 【事实】通过 |
| `vdscreen restart` | 新进程与新 displayID，模式不变 | 【事实】通过 |
| `bootout` → `bootstrap`（模拟登出→登录自启） | 先变为 `off`，重新加载 LaunchAgent 后自动恢复 `on ... 3008x1692` | 【事实】通过 |
| `vdscreen main` 切主屏 | `BoltKVM` 变为 `Main Display: Yes`，UGREEN 降为扩展屏；再次执行恢复 UGREEN 主屏 | 【事实】通过 |

LaunchAgent 关键字段【事实】：

```text
Label          = io.github.lyondan.vdscreen
RunAtLoad      = true
KeepAlive      = false
ProgramArguments = vdscreen-core 3008x1692 BoltKVM io.github.lyondan.vdscreen
```

**风险**【事实 + 推断】：`KeepAlive = false` 意味着核心进程若异常崩溃，launchd 不会自动拉起；`kickstart`/`restart` 可用，但不等于崩溃自愈。M3 的“虚拟显示看门狗”仍有必要，需在 M1/M3 验证 vdscreen 是否有内部自愈。

## 3. 捕获面

### 3.1 探针

代码：[`tools/probe-capture.swift`](../../tools/probe-capture.swift)。步骤：

1. `CGGetActiveDisplayList` 打印 displayID、bounds、pixel/logical mode、刷新率；
2. `SCShareableContent` 枚举 `SCDisplay` 的 points 尺寸；
3. 取像素面积最大的显示，按 `CGDisplayMode.pixelWidth/Height` 配置 `SCStreamConfiguration`；
4. `SCScreenshotManager` 抓一帧并保存 PNG。

构建与运行：

```bash
xcrun swiftc -O -parse-as-library tools/probe-capture.swift -o /tmp/probe-capture
/tmp/probe-capture /tmp/probe-capture.png
```

### 3.2 TCC 坑

直接从 SSH 运行探针时【事实】：

```text
CGPreflightScreenCaptureAccess = false
ERROR: Error Domain=com.apple.ScreenCaptureKit.SCStreamErrorDomain Code=-3801
"用户拒绝了应用程序、窗口、显示器捕捉的TCC"
```

原因：屏幕录制权限按“责任进程”授予，SSH 会话没有该权限，且不会弹出可交互授权。把同一探针放进已获屏幕录制权限的 GUI 应用（本次为 Terminal）启动后【事实】：

```text
CGPreflightScreenCaptureAccess = true
```

可复跑方式：把 `probe-capture` 的调用写进 `.command` 脚本，用 `open -a Terminal /tmp/run-probe.command` 启动，输出重定向到日志。M1 的采集端需要自己申请并持有该 TCC 权限，不能依赖 SSH。

### 3.3 实测输出

```text
== CG active displays (2) ==
id=1 bounds=2560x1440 modePixel=2560x1440 modeLogical=2560x1440 @30.00Hz main -
id=16 bounds=3008x1692 modePixel=6016x3384 modeLogical=3008x1692 @60.00Hz - -
== SCShareableContent ==
SCDisplay id=1  points=2560x1440 modePixel=2560x1440 frame=(0.0, 0.0, 2560.0, 1440.0)
SCDisplay id=16 points=3008x1692 modePixel=6016x3384 frame=(2560.0, 0.0, 3008.0, 1692.0)
== capture target ==
SCDisplay id=16 points=3008x1692 pixel=6016x3384
== SCScreenshotManager ==
captured image: 6016x3384 bytesPerRow=24064
saved: /tmp/probe-capture.png
```

对照【事实】：

- 虚拟屏逻辑尺寸 `3008×1692`，背板 `6016×3384`，60Hz；
- `SCDisplay.width/height` 返回的是 **points**（`3008×1692`），不是像素；
- 按 `mode.pixelWidth/Height = 6016×3384` 配置后，抓到的 PNG 就是 `6016×3384`；
- 反向验证：同一程序枚举物理 UGREEN 得到 `2560×1440`，与虚拟屏不同，排除硬编码。

### 3.4 图像证据

- PNG：`6016×3384`，约 31MB，非空、含桌面与菜单栏；
- 从 PNG 中按 1:1 裁 `1400×200` 的菜单栏区域，苹果标志与中文菜单文字边缘锐利；若只是把 `3008×1692` 放大 2×，边缘会明显发虚。

据此判断捕获是**真实背板像素**，不是逻辑尺寸上采样【事实 + 推断】。

## 4. α′ / β 初判

| 路径 | M0 后判断 |
|---|---|
| **β 传 backing 尺寸** | 直接可行：采集 `6016×3384`，客户端按 backing 1:1 绘制，由主控端合成器缩放到 3840×2160 面板，与本地 T3252U 的 `6016→3840` 路径一致 |
| **α′ 全屏切原生** | 仍需 M1 验证：要把捕获面降到 3840×2160，并在客户端切换到 1× 3840 模式；多一次缩放，且模式切换有黑屏成本 |

结论【推断】：M0 的捕获面是 6016×3384，**β 是像素等价的自然路径**；α′ 只有在 6K60 编码无法满足延迟/帧率时才值得考虑。ADR 0002 保持“提议中”，等 M1 的 4K/6K 编码延迟、码率、画质与模式切换实测再定。

关键未知【未经核实】：

- M4 Pro 的 VideoToolbox HEVC 硬件编码在 `6016×3384 @ 60fps` 下的延迟、码率与画质；
- VideoToolbox 能否同时开启低延迟码控与 4:4:4（4:2:0 会让彩色文字发虚）；
- 6K 帧在 Metal 客户端 1:1 呈现时的合成开销。

## 5. 雷雳链路基线

### 5.1 RTT

```text
10 packets transmitted, 10 packets received, 0.0% packet loss
round-trip min/avg/max/stddev = 0.180/0.617/0.971/0.183 ms
```

满足 `< 1ms` 要求【事实】。

### 5.2 吞吐

工具：[`tools/netbench.py`](../../tools/netbench.py)。数据走 `bridge0` 上的裸 TCP（不经 SSH 加密），客户端计时，服务端核对字节数。

| 方向 | 数据量 | 实测 |
|---|---|---|
| 主控端 → 被控端 | 4 GiB | `60.74 Gbit/s`，服务端收到 4294967296 字节 |
| 被控端 → 主控端 | 4 GiB | `64.00 Gbit/s`，服务端收到 4294967296 字节 |

【事实】双向均约 60 Gbit/s 量级，远高于 4K60 压缩后 50–800Mbps 的预算；链路不是瓶颈，延迟在采集/编码/解码/合成。

> 该数字是 TCP 吞吐，不是 Thunderbolt 链路标称带宽；它证明的是“当前两台机器 + 当前网桥配置”的上限余量。

## 6. 救援通道与会话

| 项 | 实测 |
|---|---|
| Screen Sharing 服务 | `com.apple.screensharing` 已加载，5900 端口返回 `RFB 003.889`【事实】 |
| FileVault | `FileVault is Off`【事实】 |
| 自动登录 | 已开启（用户名略）【事实】 |
| 当前主屏 | UGREEN（物理屏在线），虚拟屏为扩展屏，位于其右侧 `frame=(2560,0)`【事实】；`vdscreen main` 可把虚拟屏切为主屏并恢复 |
| 睡眠 | `pmset` 显示系统与显示均不自动睡眠，且有 `caffeinate` 断言【事实】 |

**判断**【推断】：

- 自动登录开启时，“登录前 VNC 救援”这一场景不成立；重启后应直接进入 Aqua 会话；
- 但自动登录 + FileVault 关闭意味着物理接触即完全控制，必须配合可信物理环境、固件密码与物理锁；
- 本次未重启机器，未实测“重启 → 自动登录 → vdscreen 自启 → VNC 可用”的完整链路。

## 7. 未验证项与风险

| 项 | 状态 | 说明 |
|---|---|---|
| 拔掉 UGREEN 后的真无头 | 未验证 | 当前是“物理屏 + 虚拟屏扩展”，不是无头；需在维护窗口拔线重测捕获面与主屏归属 |
| 睡眠/唤醒、登出、重启恢复 | 部分验证 | `bootout/bootstrap` 模拟了登录自启，未覆盖真实重启与睡眠唤醒 |
| 音频可听性 | 未验证 | 需人在被控端可听范围内确认；默认输出是外置耳机，不是 UGREEN |
| 本地 glass-to-glass 延迟基准 | 未验证 | 需要高速相机/慢动作视频；M0 计划要求，但无法由 SSH 完成 |
| 4K60 链路色度与位深 | 未核实 | macOS 未暴露 active chroma/bit depth；需采集卡或显示器 OSD |
| A′（RustDesk）限时排除 | 未执行 | 本次按显示层任务书范围执行；ADR 0001 已接受自研主路径，A′ 仍可作为半日复核项 |
| 6K60 编码可行性 | 未验证 | M1 的核心未知 |
| vdscreen 崩溃自愈 | 未验证 | `KeepAlive=false`，只能靠 launchd 手动 `kickstart` 或重新登录恢复 |

## 9. 结论

**M0 显示层门控通过**：无头被控端能创建并稳定保持 `3008×1692 HiDPI @ 60Hz` 虚拟显示，ScreenCaptureKit 能按 `6016×3384` 原生背板采集，链路吞吐与 RTT 远优于预算。

**M0 整体尚未关闭**：真无头、睡眠/重启恢复、音频可听性、本地延迟基准与 A′ 排除项仍需人工验证；其中拔线与听音无法通过 SSH 完成。

**下一步（M1）**：先做 6016×3384 @ 60fps 的 HEVC 硬编/硬解可行性小实验，再决定 β 还是 α′；同时验证 4:2:0 与 4:4:4 对彩色文字的影响。
