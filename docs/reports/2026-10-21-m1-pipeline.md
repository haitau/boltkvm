# M1 管线报告：α′ 4K 端到端闭环已跑通

- 日期：2026-10-21
- 目标：ScreenCaptureKit → VideoToolbox HEVC 低延迟硬编 → 雷雳 TCP → 硬解 → Metal 1:1 上屏
- 结论：**α′ 最小闭环跑通**；当前约 49fps、编码延迟约 19ms，尚未达到 60fps 与 <33ms 端到端验收，但路径成立。

## 1. 实现

代码：Swift Package [`Package.swift`](../../Package.swift)，单一可执行文件 `boltkvm`，子命令：

```bash
boltkvm server --width 3840 --height 2160 --port 7474 --seconds 30
boltkvm client --host <mini> --port 7474 --seconds 12 --render --switch-mode
```

| 模块 | 实现 |
|---|---|
| 采集 | ScreenCaptureKit，6K 虚拟屏缩放到 3840×2160，420v，60fps 目标 |
| 编码 | VideoToolbox HEVC，`EnableLowLatencyRateControl`，`RealTime`，无帧重排，KeyFrameInterval=60 |
| 传输 | TCP + `TCP_NODELAY`，20 字节头 + format/frame 包，AVCC NAL |
| 解码 | VideoToolbox 硬解，实时模式 |
| 呈现 | Metal `CAMetalLayer`/`MTKView`，YCbCr BT.709 着色器，全屏 1:1 |
| 模式切换 | 进入时切到 1× 3840×2160，退出恢复原 3008×1692 HiDPI |

## 6. 本轮补充实测（60fps、延迟与编码器对比）

### 60fps 与延迟

调整服务端 `queueDepth=8`、`minimumFrameInterval=0`、去掉低延迟码控后，4K 真实桌面/测试图达到：

```text
server: fps=59.9 dropped=0 encLat=20~23ms
client: decode fps=60.3 failed=0
        recv p50=21.6ms p95=22.7ms
        decodeLatency p50=24.1ms p95=25.3ms
        render (displaySyncEnabled=false) p50=33.9ms p95=34.7ms
```

- 时钟同步：客户端/服务端握手 RTT 约 1.4–2.0ms，offset 约 2ms；延迟数字已扣除时钟偏差。
- `capture→decode` P95 已低于 33ms；`capture→present` P95 约 34.7ms，加上面板扫描尚未测，端到端仍略超 33ms。
- 关闭 Metal 层 `displaySyncEnabled` 把 render P95 从约 58ms 降到 34.7ms，代价是可能撕裂。

### 编码器对比（4K 真实测试图）

| 编码器 | 吞吐 | 平均编码延迟 | 码率 | 备注 |
|---|---|---|---|---|
| HEVC Main（硬件） | 60fps | 22.9ms | 6–17Mbps | 当前主路径；需要 4 帧在途才能维持 60fps |
| H.264 High（硬件） | 55fps | 57.7ms | 2.5Mbps | 延迟更差，排除 |
| **ProRes 422（硬件）** | 56.7fps | **8.85ms** | **561Mbps** | 全 I 帧、4:2:2 10-bit；编码延迟最低 |

结论【事实 + 推断】：

- HEVC 的 ~20ms 编码延迟不是 CPU 或吞吐瓶颈，而是编码器管线延迟；减少在途帧会掉到 25fps，不能靠队列优化解决。
- **ProRes 422 是唯一能把编码延迟压到 10ms 以内的 VideoToolbox 路径**；561Mbps 相对于 60Gbps 雷雳链路仍有余量，且全 I 帧允许客户端直接丢旧帧，天然适合低延迟。
- H.264 比 HEVC 更慢，排除。
- VT 公开的 HEVC Profile 只有 Main / Main10 / Main42210 / Monochrome，**没有 4:4:4**；自研路径的色度只能在 HEVC 4:2:0 与 ProRes 4:2:2 之间定档。

### 画质

用 6016×3384 测试图（文字、彩条、棋盘、细线、渐变）做 α′ 远程抓帧与本地 6K→4K 参考对比：

- 原始 SSIM 约 0.77–0.83，但 luminance 线性拟合后为 **0.988**；差异主要来自服务端 `CIImage` 参考帧的 YCbCr→RGB 色彩解释与客户端 shader 不一致，以及两次抓帧时刻不同。
- 该结果**不能**直接作为“像素等价通过”的证据；需要同一静态帧、同一色彩转换路径的参考图再测。

### 下一步

1. 将 M1 主路径切到 **ProRes 422**，实现客户端 ProRes 硬解与 8/10-bit 422 上屏，验证端到端 P95；
2. 固定一张静态测试图，用同一 YCbCr→RGB 转换生成参考帧，重测 SSIM；
3. 若 ProRes 带宽/解码在客户端不成立，再回退 HEVC 4:2:0。


## 7. ProRes 422 结果（2026-10-21）

M1 主路径已切到 ProRes 422（服务端 `--codec prores`，客户端 422v 硬解 + Metal）：

```text
server: fps=59.9 dropped=0 encLat=9.16ms bitrate=658Mbps
client: decode fps=60.9 failed=0
        recv p50=10.9ms p95=11.9ms
        decodeLatency p50=12.7ms p95=13.7ms
        render p50=17.6ms p95=18.2ms (capture→present)
```

- 60fps 稳定，0 丢帧；编码延迟从 HEVC 的 ~22ms 降到 **~9ms**。
- capture→decode P95 **13.7ms**；capture→present P95 **18.2ms**，距 33ms 有约 15ms 余量（尚未含面板扫描）。
- 码率约 **658Mbps**（≈82MB/s），占雷雳 60Gbps 链路的约 1%；全 I 帧，客户端可直接丢旧帧。

### 画质（ProRes，4K 1:1）

用 6016×3384 测试图缩放到 3840×2160 作为理想参考，与客户端窗口抓帧比较：

| 区域 | SSIM | PSNR |
|---|---|---|
| 全图（去掉菜单栏/底栏） | **0.9839** | 30.20dB |
| 文字区 | 0.9904 | 30.31dB |
| 细网格 | 0.9871 | 37.44dB |
| 2px/4px 彩色棋盘（最坏色度） | 0.9622 | 24.27dB |

- 全图 SSIM > 0.98；彩色高频棋盘低于 0.98，主要是 **SCK 采集本身是 4:2:0**，色度细节在编码前已丢失，ProRes 4:2:2 只能保留到这一层。
- VT 公开的 HEVC Profile 没有 4:4:4；若要进一步提高彩色边缘，需要 SCK 输出 BGRA + ProRes 4444，属于后续可选优化。

### 结论

- **α′ + ProRes 422** 是当前最优组合：60fps、capture→present P95 18.2ms、SSIM 0.984。
- HEVC 4:2:0 保留为低码率回退（约 17Mbps、22ms 编码延迟）。
- 剩余验收：glass-to-glass 相机实测（含面板）、窗口化模式、真实动态内容下的码率上限。

## 10. M1 结论

M1 的技术问题已经回答：

- 像素路径：**α′**；
- 编码：**ProRes 422**（HEVC 4:2:0 回退）；
- 色度：4:2:2（VT HEVC 无 4:4:4；SCK 源为 4:2:0）；
- 帧率：60fps；
- 软件链路 capture→present P95 18.2–27.6ms；

glass-to-glass 相机实测与 4:4:4/BGRA 优化作为后续验证项，不再阻塞 M1 技术闭环。
