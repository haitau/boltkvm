## 变更范围

1. **24-bit / 48 kHz 音频**：认证后协商 packed int24；服务端 `AVAudioConverter` 转 int32 后取高 24 位，客户端解包到 float32 播放。旧端没有能力位时自动回退 int16，协议字节 6 兼容原有保留字节。
2. **选中音频的本地静音语义**：首个音频包发送 `muteLocalOutput`，被控端只静音默认输出，不暂停 Now Playing，避免“暂停了正在转发的源”。
3. **换输出设备的过渡**：客户端 suspend 旧图、静音主控端整机输出 2.5 s、合并 CoreAudio 通知、0.6 s 后只重建一次，并向被控端发一次 `pauseMedia`。
4. **本地音量键**：选中音频时音量键不再转发，避免 mini 的 HUD 忽大忽小。
5. **全屏工具栏点击穿透修复**：沿用 v0.12.1 的三层输入防护，本版未回退。
6. **应用内版本标识**：应用菜单固定显示短版本与构建号；被控端设置面板标题栏/右上角、主控端连接列表标题栏与底部、主控窗口标题都显示 `0.13 (构建号)`，不再只能依赖 About 面板。

## 24-bit 具体行为

- 能力位：`authOk` flags 追加 `FLAG_SUPPORTS_AUDIO_24`（值 2），服务端 flags 变为 `0x03`。
- 协商：客户端在 `SessionConfig` 字节 6 写 `AudioWireFormat.int24`；无尺寸请求时发送 `0x0` config，服务端只读取音频格式，不重建虚拟屏。
- 线格式：48 kHz / 2 ch / 3 bytes/sample = 6 bytes/frame，约 **2.30 Mbps**；int16 仍是 4 bytes/frame、约 1.54 Mbps。
- 播放：24-bit 解包后左移 8 位再归一化到 float32；当前 macOS 不接受 int32 播放连接（实测 `-10868 FormatNotSupported`），所以不能用 int32 直接接 `AVAudioEngine`。
- 记录：`--audio-record` 在 24-bit 会话下写 32-bit float 诊断文件（float32 可完整容纳 24-bit 尾数），不是 packed 24-bit 文件。

## 2026-10-28 音频修正：多输出设备与 CLI

用户实机报告：主控端选择音频后，mini 扬声器仍然很响，Pro 耳机没有声音。日志把两个问题分开了：

- mini 的默认输出是 **「多输出设备」**（`~:AMS2_StackedOutput:0`），它本身没有 mute/volume 属性。旧实现只查默认设备，失败后仍打印 `muted controlled Mac output`，所以实际上没有静音；这就是 mini 外放继续响的直接原因。
- 修正：当默认输出是 aggregate/multi-output 且没有原生控制时，枚举 `kAudioAggregateDevicePropertyFullSubDeviceList`，跳过虚拟设备，逐个静音/置零物理子设备；状态文件按成员保存原 mute/volume，断开或崩溃恢复时逐个还原。`AudioOutputMute.start()` 现在返回是否真的静音，server 只有在成功时才记录“已静音”。
- mini 实测：`多输出设备` 的 `Mac mini扬声器` 从 mute=0 变为 1；断开后恢复 0，日志 `muted local output ... via 1 aggregate members` / `restored local output ... aggregate members`。
- CLI `client --audio` 也已补齐 24-bit 协商和首个包 `muteLocalOutput`；此前 CLI 总是 int16，且不请求本地静音。
- 客户端播放日志现在写明实际输出设备、UID、音量与 mute，例如 `外置耳机 [uid=BuiltInHeadphoneOutputDevice volume=0.18 mute=0]`，用于区分“路由到错误设备”和“播放图没有声音”。

Pro 侧没有发现播放路径静音：用户那次会话的 CoreAudio 日志显示播放器启动的是 `BuiltInHeadphoneOutputDevice`，应用日志也收到并调度了 58.8 s、RMS -28.6 dBFS 的 int24 音频。为排除 24-bit 播放图问题，用 BlackHole 环回做了不发声验证：同一客户端图播放 `Glass.aiff`，录到的环回文件最大 **-14.1 dB**，不是静音。实际耳机是否听到仍需要用户复核（见下）。

## 2026-10-28 关闭主控窗口：先暂停，再恢复被控端输出

之前关闭主控窗口只做 `disconnect()`：服务端在 session 结束时恢复本地静音，但 Now Playing 仍在播放，于是声音从 mini 扬声器重新冒出来。现在：

- 主控端 `disconnect(pauseRemoteMedia: true)` 在关闭连接前发送一次 `pauseMedia`；`ClientController.windowWillClose` 和 `shutdown()` 都走这条路径。
- 服务端在 session 结束时，只要收到过 `muteLocalOutput`（即使设备静音失败，`clientAudioActive` 仍为真），就**先**在主线程暂停当前 Now Playing，**再**恢复本地输出；这样即使客户端崩溃、网络断开或 pause 包在关闭时丢失，也不会在恢复输出后突然外放。
- **`pause` 命令被 MediaRemote 接受，不等于播放器已经停止**。第一版在同一 tick 恢复输出，实际会泄漏一小段声音。现在用 `MRMediaRemoteGetNowPlayingApplicationIsPlaying` 轮询 Now Playing：连续确认停止后，再等 250ms 稳定窗口才恢复 mute/volume；查询不可用时先保持 600ms，超时未确认再额外保持 500ms。顺序始终是 pause → 确认停止 → 恢复输出。

- `swift test`：**102 项通过、1 项跳过、0 失败**；跳过项是 `AudioRouteChangeTests`（需要显式音频输出环境）。
- `swift test --filter ProtocolTests`：14 项通过；覆盖 config 字节 6、`0x0` 音频专用配置、24-bit 打包/解包的符号与高位。
- `swift test --filter Audio24Tests`：3 项通过；覆盖 float32 播放图、静音包调度、float32 记录文件帧数。
- 本机 → mini 的 record-only 端到端（不发声）：客户端日志 `sent config 0x0 audio=int24`；mini 日志 `audio source ... target=int24` 与 `audio=182 pkts/2.3Mbps`；客户端记录 **178,560 帧 / 3.72 s**，日志 `format=int24`。
- 多输出设备静音：silent source + 真实 server；播放期间 mini 内置扬声器 mute=1，断开后 mute=0；server 日志 `muted ... via 1 aggregate members`、`restored ... aggregate members`。
- 关闭暂停：silent source + CLI 断开（不发声）；mini 日志按顺序出现 `audio: client ended with audio active; pausing media before unmute`、`media: paused the current Now Playing app`、`audio: Now Playing confirmed paused; restoring output`、`audio: restored local output ... aggregate members`。0.13 (237) 上实测断开后 0.15s 扬声器仍是 mute=1，约 0.35s 才恢复 mute=0，说明没有在同一 tick 恢复输出。GUI 关窗路径还会先发一次 `pauseMedia`，服务端兜底覆盖命令丢失。真实网易云/Apple Music 的关窗暂停仍需用户确认。
- 24-bit 环回：Pro 默认输出临时设为 BlackHole，播放 `Glass.aiff`，环回 WAV 最大 **-14.1 dB**；证明 int24 解码/调度图有实际波形。测试期间耳机与扬声器均未发声。
- 部署：Pro 与 mini 的 `/Applications/BoltKVM.app` 均为 `0.13`；mini 部署日志确认“签名身份未变，保留现有 TCC 授权”。

## 为什么撤回标签 / 0.13 的门槛

撤回的直接原因是标签尚未 push，而发布说明把被控端权限写成了“屏幕录制 / 辅助功能 / 输入监控”三项；应用配置界面实际只有**屏幕录制、辅助功能**两项。被控端 GUI 不需要输入监控：GUI 主控端用窗口内 `NSEvent` 本地监听，只有 CLI `--input` 的 `CGEventTap` 才需要输入监控；「本地网络」是 macOS 15+ 连接雷雳桥时的独立授权提示，不是应用设置面板里的第三个权限按钮。

不需要把“所有能想到的问题”都清零才能发 0.13。发布门槛应是：

- **阻塞项清零**：已知会导致崩溃、数据丢失、核心功能不可用、错误权限指引，或本次新功能完全未验收的问题；
- **已知非阻塞项写明**：96 kHz、睡眠/唤醒、物理拔插、Glass-to-glass 基准等，可以作为边界发布；
- **构建与 CI 通过**：本地 `swift test` 已通过，但推送前 CI 尚未跑过这批提交；
- **用户实机验收**：24-bit 实际听感、换耳机后的停止/恢复、mini 的静音恢复。

当前阻塞项不是“无数问题”，而是三类：实际音频听感未验收（尤其 Pro 耳机）、mini 两项权限未由用户确认、CI 尚未跑这批提交。其余已知项已在 [open-items](../plans/open-items.md) 中分类，不要求全部改完。
