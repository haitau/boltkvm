# B5 / B7：GUI 客户端帧率与延迟优化报告（2026-10-23）

## 1. 背景与目标

早期测试中观察到客户端瞬时帧率（58 fps）、长跑平均帧率（25.1 fps）与 CLI 解码帧率（57.7 fps）不一致，且端到端延迟偶发飙升至秒级。本轮排查定位并修复了三个导致延迟放大的缺陷，并将 GUI 呈现模式从 60Hz 定时回调改为到帧即时泵送（B7），确立了最终的两档延迟 SLO：

- **解码链路（采集→解码）SLO**：P95 < 33 ms；
- **GUI 呈现链路（采集→上屏，不含输入反向上行）SLO**：P95 < 50 ms。

## 2. 测试环境

| 项目 | 配置 |
|---|---|
| 主控端 | MacBook Pro（M5 Pro），主屏 3008×1692 @2x |
| 被控端 | Mac mini（M4 Pro），内建虚拟屏 3008×1692（像素 6016×3384），ProRes 422 |
| 网络链路 | 雷雳网桥（Thunderbolt Bridge），`<mini 桥接地址>:7474` |
| 画面负载 | 被控端运行 `boltkvm-server inputprobe --interval-ms 16`（每秒 62 次鼠标微移，持续触发画面更新） |

## 3. 修复三个延迟放大问题（B5）

1. **限制 VideoToolbox 解码在途帧数**：此前服务端按 ~60 fps 推流，当客户端窗口被遮挡或瞬时繁忙时，未解码帧在 VideoToolbox 内部无界堆积，导致画面滞后达 3 秒（`p50 = 3198 ms`）。现为解码器增加 `inFlight = 2` 信号量上限，超出时直接丢弃旧帧。
2. **握手阶段完成初始时钟同步**：此前 `timeSync` 请求仅在视频流灌满 TCP 缓冲区后发送，往返受队头阻塞影响导致 RTT 从 19 ms 暴涨至 6 秒，算出的时钟偏移失真。现改为在 `authOk` 载荷中直接携带服务端微秒时间戳（此时尚无视频帧排队），后续 `timeSync` 仅在 RTT 不劣于历史最佳值时更新偏移。
3. **动态重建虚拟屏后唤醒显示器**：客户端通过 `config` 包请求切换分辨率并重建虚拟屏后，新虚拟屏因缺少用户活动声明被电源管理限频在 ~30Hz。在重建后补充调用 `IOPMAssertionDeclareUserActivity`，采集帧率立即恢复至 57.8–60.0 fps。

### 3.1 修复后解码链路实测（CLI 客户端）

| 轮次 | 解码 fps | Decode P50 | Decode P95 | Recv P50 | Recv P95 |
|---|---|---|---|---|---|
| 修复前（队列积压） | 24.6 | 3198.1 ms | 3229.2 ms | — | — |
| 修复后 #1（3008×1692） | 57.7 | 24.6 ms | **25.4 ms** | 22.4 ms | 23.2 ms |
| 修复后 #2（3008×1692） | 54.1 | 24.9 ms | **26.6 ms** | 22.8 ms | 24.5 ms |
| 修复后 #3（动态切换 2560×1440） | 58.0 | 25.4 ms | **27.0 ms** | 23.7 ms | 25.2 ms |

解码链路 P95 稳定在 **25.4–27.0 ms**，满足 `< 33 ms` 的解码 SLO。

> 解码吞吐三轮为 57.7 / 54.1 / 58.0 fps，README 的区间应取 54.1–58.0；`57.6` 是更早报告里的上限值，不是本轮下界。

### 3.2 窗口遮挡与 TCP 反压的关系

当 GUI 客户端窗口被其他窗口完全遮挡或退入后台时，macOS 合成器会将不可见窗口的绘制频率降至 18–28 fps，进而通过 TCP 反压与服务端发送队列上限（4 帧 / 8 MB）触发服务端主动丢帧；一旦窗口回到前台，帧率立即恢复满帧，且因队列有界，P50/P95 延迟全程保持平稳、不再累积落后。

## 4. 消除呈现链路排队等待（B7）

### 4.1 根因分析

修复上述三项后，解码链路 P95 为 25.4 ms，但 GUI `capture→present` P95 仍为 37.6–41.9 ms，中间多出约 12–14 ms。分段计时（`render split`）显示瓶颈不在 Metal 纹理上传或着色器，而在 `MTKView` 默认采用的 60Hz 显示链路（`CVDisplayLink`）定时回调：解码完成的帧必须等待下一次 16.7 ms 刷新 tick 才能触发绘制，**平均排队等待 8.4 ms**。

### 4.2 优化方案：到帧即时泵送（Draw Pump）

在 `Renderer.swift` 中将 `MTKView` 设为 `isPaused = true`（停用定时 tick），改为在解码回调 `submit()` 收到新帧时立即切回主线程调用一次 `view.draw()`；同时使用配额为 2 的信号量（`inFlight`）保护可绘制缓冲，确保 `currentDrawable` 永不阻塞主线程（可通过环境变量 `BOLTKVM_DISPLAY_LINK=1` 切回旧的定时回调模式）。

### 4.3 实测对比（6016×3384 ProRes 422，60 秒稳态窗口）

| 渲染调度模式 | 呈现 fps | Capture→Present P50 | Capture→Present P95 | Decode→Submit 排队 P95 |
|---|---|---|---|---|
| 60Hz 显示链路（`BOLTKVM_DISPLAY_LINK=1`） | 59.5 | 35.8 ms | 37.6 ms | 8.4 ms |
| **到帧即时泵送（默认）** | **60.0** | **31.0 ms** | **33.2 ms** | **0.0 ms** |

连续三个独立会话复测，到帧泵送模式下的 `capture→present` P95 均稳定在 **33.2–33.3 ms**，比 50 ms GUI SLO 留有约 17 ms 余量。

## 5. 复现命令

```bash
# 被控端：启动持续画面变化探针
ssh <mini> 'nohup /Applications/BoltKVM.app/Contents/MacOS/boltkvm-server inputprobe --seconds 800 --interval-ms 16 &'

# 1. 测量解码链路（CLI）
.build/release/boltkvm client --host <mini 桥接地址> --port 7474 --seconds 45

# 2. 测量 GUI 呈现链路（默认到帧泵送 vs 显示链路对照）
open dist/BoltKVM.app
BOLTKVM_DISPLAY_LINK=1 open dist/BoltKVM.app
grep -E "render.win|render split" ~/Library/Logs/BoltKVM.log | tail -20
```

## 证据分级

- 【事实】3.1 表三轮解码 fps 与 P50/P95（CLI 客户端）、4.3 表 60 秒稳态窗口的呈现 fps 与 `capture→present` P50/P95，均为报告记录的实测表格。
- 【事实】三处修复（解码 `inFlight = 2`、`authOk` 携带服务端时间戳、重建虚拟屏后 `IOPMAssertionDeclareUserActivity`）与 `Renderer.swift` 的到帧泵送、`BOLTKVM_DISPLAY_LINK` 开关，是代码改动本身。
- 【推断】「中间多出的 12–14 ms 来自 60Hz 定时回调、平均排队 8.4 ms」是基于 `render split` 分段计时的解释，报告未贴出分段计时的原始行。
- 【推断】3.2 节「遮挡 → 合成器降帧 → TCP 反压 → 服务端在 4 帧 / 8 MB 上限处丢帧」是机制解释，报告未给出该场景下的逐项计数。
- 【未经核实】原始日志未随报告入库（只给了 `grep` 复现命令），三轮与三个会话的独立复测无法在此核对；`57.6 fps` 来自更早的报告，不是本轮下界，README 的 54.1–58.0 才对应本轮三轮。
