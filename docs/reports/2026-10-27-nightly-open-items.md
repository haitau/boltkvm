## A-1 被控端本地静音

实现：

- `AudioOutputMute` 在 SCK 采集启动成功后静音默认输出；客户端断开恢复。
- 优先 `kAudioDevicePropertyMute`，设备不支持时退回音量 0；默认输出变化时先恢复旧设备，再静音新设备。
- 改设备前写 `~/Library/Application Support/BoltKVM/mute-state.json`；`SIGKILL` 后下次服务端启动先恢复，避免永久静音。
- `--no-local-mute` 可关闭。

验证：

1. 服务端 `--audio`，客户端 `--audio-record /tmp/mute2.caf`，服务端播放测试音：
   - 连接期间 `osascript -e 'get volume settings'` → `output muted:true`；
   - 断开后 → `output muted:false`；
   - 录音分析仍有 −29.4 dBFS 的测试音，说明 SCK 采集在静音之前，远端不被连带静音。
2. 默认输出从内置扬声器切到 BlackHole 再切回：
   - 日志依次 `muted ... 内置扬声器` → `restored ... 内置扬声器` → `muted ... BlackHole` → `restored ... BlackHole` → `muted ... 内置扬声器` → 断开 `restored ... 内置扬声器`。
3. `kill -9` 服务端：
   - 静音保持，marker 存在；重启服务端（无客户端）立即打印 `restored a stale local-mute marker`，`output muted:false`，marker 删除。
   - marker 里新增所属 pid；静音中的服务端 A 尚在运行时启动服务端 B，B 打印 `mute marker is owned by live pid ...; leaving it alone`，A 的静音保持。
4. `--no-local-mute` 与不开 `--audio` 两种情况下，连接期间均 `output muted:false`。

未验证：跨机、蓝牙耳机真实切换、多输出设备（聚合/多输出）上的静音语义。

## A-2 主控端输出变化 → 被控端暂停媒体

实现：

- `AudioPlayer` 监听 CoreAudio 默认输出变化，0.5 s 防抖；回调放在独立队列，不被可能卡住的 `AVAudioEngine` 重建阻塞。
- 客户端新增 `RemoteAction.pauseMedia`（7），只在主控端播放转发音频时发送；录音-only 不发送。
- 服务端用 MediaRemote `MRMediaRemoteSendCommand(1, nil)` 暂停当前 Now Playing 应用；失败再发 stop(3)，不退出应用。
- 0.5 s 防抖窗口内断线时，`finished` 会丢弃未发出的暂停请求。
- GUI（`ClientSession`）与 CLI 客户端都接线。

验证：

1. 服务端 `--audio --no-local-mute`，客户端 `--audio`，把默认输出从内置扬声器切到 BlackHole 再切回：
   - 客户端：`audio: output route changed; asked server to pause media`；
   - 服务端：`command: pauseMedia`、`media: paused the current Now Playing app`。
2. `AudioRouteChangeTests` 真实切换输出设备通过，并断言 `onOutputRouteChange` 回调被触发；客户端音频图也完成重建（graph #1→#2→#3）。
3. `RemoteAction.pauseMedia == 7` 有单测，旧命令值不变。

未验证：真实网易云音乐/Music 的暂停效果。曾用 `orpheus://song/186016` 启动网易云，进程能起来，但 `MRMediaRemoteGetNowPlayingInfo` 仍返回 `no info`（无法确认是否开始播放），不能据此判定暂停有效。MediaRemote 返回成功只能证明命令被系统接受，不能证明具体播放器响应。若明早网易云不响应系统 Now Playing，需要补 AppleScript/媒体键回退。

## A-3 剪切板互通

实现：

- 新增 `clipboard`（13）与 `fileTransfer`（14）包；非文件项 256 KB 分块、默认单次 ≤512 MB；文件 1 MB 分块，默认按「可用磁盘 − 20 GB」，可再加 GB 上限。
- 支持纯文本、HTML、RTF、PNG（TIFF 转 PNG）、文件/文件夹内容；接收端 `~/Downloads/BoltKVM Clipboard/`，目录用 `ditto` 打包/解包并校验 zip 条目路径，逐文件 SHA-256。
- `changeCount` + 内容哈希防回环；跳过 `ConcealedType`/`TransientType`/`AutoGeneratedType`；客户端设置开关，默认开启；服务端 `--no-clipboard`。
- `BOLTKVM_CLIPBOARD_DIR` 仅测试用；正常路径仍是 Downloads。

验证（本机回环，两端同一粘贴板）：

| 内容 | 结果 |
|---|---|
| 纯文本 48 B | 客户端 1 块发送，服务端应用，粘贴板内容正确 |
| HTML/RTF 116 B | 2 个表示发送，应用后 `clipboard info` 仍有 HTML/UTF-8 |
| 17,884,060 B PNG | 69 块发送，服务端应用 17,884,078 B |
| 5,242,880 B 文件 + 1,396 B 文件夹（含嵌套目录） | 2 项、SHA-256 校验通过，文件与目录结构正确 |
| 52,428,800 B 文件 | 1 MB 分块完整传输，接收端 SHA-256 与源文件一致 |
| 1 MB 上限 + 17 MB PNG | 两端均记录 `exceeds the 1 MB item limit` 并跳过 |
| 含 `/etc` 软链的文件夹 | 发送端记录 `symlinks are not supported` 并跳过，接收目录为空 |
| 0 B 文件 + `中文 文件.txt` | 分别落盘，13 B 中文内容正确；同机回环出现带 `2` 的副本 |
| 清单 size 溢出 | 单测拒绝两项 `Int64.max` 之和，不触发 trap |
| 全量测试 | 91 项通过，1 skip（硬件音频测试默认跳过） |

已知现象：同一台机器回环时两端共享粘贴板，A 发、B 也发，接收目录会出现 `big 2.bin`、`folder 2` 两份；跨机只有接收端落盘，不应出现该现象，但尚未跨机验证。

未验证：跨机、GUI 复选框实际点击、真实 `~/Downloads` 写入（CLI 测试进程受 DSH 沙箱限制，改用 `BOLTKVM_CLIPBOARD_DIR`）、超大文件/长时间大流量下的内存与磁盘表现、zip 内符号链接拒绝的实际提示。
