# boltkvm 项目设计文档

> 状态：M1–M3 已实现，8 小时长稳已验证（2026-10-22），重启恢复实测两轮（自动登录 + 服务自启 + SSH/VNC 救援）。剩余项集中在 [未完成事项](../plans/open-items.md)：输入连续性、音频隔离、睡眠唤醒、拔插雷雳、VNC 预登录、TCC 升级演练。文中标注【推断】的条目仍未实测。

## 1. 目标

在 MacBook 外接的 4K 显示器上，以接近本地的清晰度与延迟操作一台无头 Mac mini 的完整桌面：

- 目标显示模式：3008×1692 HiDPI @ 60Hz；
- 端到端延迟：输入到上屏 < 33ms，< 16ms 为加分项；
- 音频默认完全分开：被控端声音由被控端本机输出，不进入传输链路，不劫持主控端系统默认输出；显式 `--audio` 时才转发（2026-10-22 起可选）；
- 控制方向固定为主控端 → 被控端；被控端不接本地键鼠，从拓扑上消除双向控制回环；
- 雷雳 5 直连，不依赖公网。

可度量的目标是**像素等价**：被控端桌面在主控端显示器上的观感，与主控端本地以 3008×1692 HiDPI 驱动同一显示器时逐像素一致。

## 2. 非目标

- 不做跨公网远程桌面；先解决同一桌面、同一网段、同一对设备。
- 不做双向控制；控制方向固定为主控端 → 被控端。
- 不以“必须自研”为前提；现成方案能满足验收指标，就不写代码。
- 不采用物理切换显示器的方案；主控端显示器始终由主控端驱动。
- 先作为个人工具跑通；开源产品化是后续目标，不反向绑架当前设计。

## 3. 目标环境

| 项 | 参考配置 |
|---|---|
| 被控端 | Apple silicon Mac mini，macOS 27，目标运行状态为无头 |
| 主控端 | Apple silicon MacBook Pro，macOS 27 |
| 连接 | 雷雳 5 线直连（Thunderbolt Bridge）；链路 80Gbps 双向，Boost 最高 120Gbps |
| 客户端显示 | 32 英寸 4K（3840×2160）@ 60Hz |
| 目标显示模式 | 3008×1692 @ 60Hz（HiDPI 缩放；帧缓冲 6016×3384 → 缩放到 3840×2160 面板） |
| 网络 | 独立雷雳网桥子网（示例网段 `<bridge-subnet>`，实际以部署为准），不依赖公网 |
| 硬件约束 | 参考部署不新增硬件；现有显卡欺骗器（1080p/1440p/4K）可用于对照实验 |

开发机可能临时连接显示器用于配置；目标运行状态仍以无头为准。

## 4. 为什么是两台机器

- 被控端承载大量常驻自动化任务，并分担开发工作，需要长期在线；
- 主控端是移动设备，不能承担 24/7 常驻；
- 这些任务与开发环境需要完整桌面会话，因此远程 GUI 是刚需，不是附加功能；
- 自动化控制面与 GUI 通道必须分离：自动化由 SSH/launchd 管理，GUI 通道故障不得影响自动化任务的运行与恢复。

## 5. 已评估方案与结论

### 5.1 macOS 自带屏幕共享

- 标准连接基于 VNC/RFB，清晰度与流畅度受协议上限限制；
- 高性能连接比标准模式好，但分辨率上限为 4K / 1080p HiDPI，且音频会回传到主控端；
- 原生支持聚焦搜索、调度中心、显示桌面等系统级交互，这是第三方远控最难替代的部分；
- **结论：不作为主方案**；保留为标准 VNC 救援通道，用于处理 TCC 弹窗与故障修复。

### 5.2 Sunshine / Moonlight

- 控制不顺畅，鼠标键盘映射不自然；
- macOS 作为宿主端的成熟度低于 Windows/Linux；
- 清晰度根因在客户端：moonlight-qt #1185 指出 macOS 客户端在 HiDPI 缩放下会二次重采样，截至 2026-10-21 仍为 open；
- **结论：已放弃，不再复测。**

### 5.3 显卡欺骗器与 EDID

- 显卡欺骗器可提供 1080p / 1440p / 4K，但无法直接匹配 3008×1692；
- 关键不在“有没有欺骗器”，而在 EDID 是否向 macOS 暴露目标分辨率与刷新率；
- 有实测表明：HDMI 直连只能得到 LoDPI 的 3008×1692；换用 EDID 中声明 3008×1692@60Hz 的 USB-C→HDMI 转接器，才得到 3840×2160 缩放后的 3008×1692 HiDPI。

### 5.4 虚拟显示

- 早期验证已证明 `CGVirtualDisplay` 可以在无头 Mac 上创建 3008×1692 虚拟屏；
- 本项目只采用开源实现（如 `vdscreen`、`vdisplay`）复验该能力；
- 自研不能绕过虚拟显示：ScreenCaptureKit 只能采集已存在的显示。

### 5.5 双向控制死循环

- 两端同时运行被控端服务并互相控制时，输入事件会在两端之间回环；
- 这不是“互控”的必然结果，而是缺少单写者仲裁；
- 本项目的拓扑是主控端只做采集与渲染、被控端只做虚拟显示与输入注入，主控端不运行被控端服务，从根上消除回环；
- 服务端仍应拒绝第二个输入源，作为廉价兜底。

## 6. 技术边界

以下为方案判断的前提。标注：**【事实】** 有来源或已实测；**【推断】** 工程推导，需实测；**【未经核实】** 无一手来源。

1. **雷雳 5 是链路规格，不是实际吞吐。**【事实】TB5 规格为 80Gbps 双向、Boost 最高 120Gbps；Thunderbolt Bridge 的 TCP/IP 实测吞吐远低于链路（TB4/USB4 约 11Gbps/方向，macOS + TB5 尚无公开可信实测）。本项目 4K60 压缩后约 50–150Mbps，即使高码率 300–800Mbps，链路余量仍是数量级级别；真正的延迟在采集、编码、传输、解码、合成。
2. **Apple 高性能屏幕共享有分辨率天花板。**【事实】虚拟显示上限为 4K（3840×2160），HiDPI 上限为 1920×1080。3008×1692 HiDPI 的帧缓冲是 6016×3384，像素量约为 4K 的 2.4 倍，超出该模式能力。
3. **Apple silicon Mac mini 无头时会自动创建 1080p 虚拟显示。**【事实】显卡欺骗器不是必需项；问题在 EDID 与可用分辨率，不在“没有显示信号”。
4. **3008×1692 HiDPI 依赖 EDID 或虚拟显示。**【事实】无头场景下由 `CGVirtualDisplay` 提供；物理显示场景下取决于 EDID。
5. **音频回传是选型硬约束。**【事实】高性能屏幕共享会把被控端音频送到主控端；若无法关闭，该路径直接出局。
6. **控制环是仲裁问题。**【推断】正确的不变量是“同一时刻只有一个输入注入者”。本项目的拓扑天然满足该不变量，服务端拒绝第二输入源作为兜底。
7. **VNC 与高性能模式不是一回事。**【事实】标准屏幕共享基于 VNC；高性能模式是 Apple 私有低延迟协议。
8. **第三方工具的延迟数字多来自聚合评测，不是独立基准。**【事实】需要本机实测确认。
9. **清晰度损失发生在客户端呈现，不在传输。**【事实 + 推断】主控端以 3008×1692 HiDPI 运行时，帧缓冲是 6016×3384，再由系统缩放到 3840×2160 面板。客户端收到 4K 帧会先被放大到 6016×3384、再缩回 3840×2160，二次重采样导致发糊。实现像素等价有两条路：
   - **α′ 全屏切原生**：被控端采集输出 3840×2160；主控端进入全屏时把显示器临时切到原生 1x 3840×2160，帧 1:1 上屏，退出时恢复。代价是模式切换黑屏（预计 1–2s，【推断】）。窗口化接受缩放。
   - **β 传 backing 尺寸**：传输 6016×3384，客户端按 backing 像素 1:1 绘制，由主控端合成器执行与本地相同的缩放。全屏与窗口均等价、无需切模式；代价是像素量为 4K 的 2.45 倍，编码延迟与码率上升。
10. **自研不能绕过虚拟显示。**【事实】ScreenCaptureKit 只能采集已存在的显示；无头被控端必须先有 3008×1692 HiDPI 的虚拟或物理显示。
11. **色度采样影响文字清晰度。**【推断】4:2:0 会让彩色文字与细线边缘发虚；VideoToolbox HEVC 4:4:4 硬件编码能否同时启用低延迟码控【未经核实】，需实测。退路是 4:2:0 + 高码率。
12. **点对点直连不需要 WebRTC。**【推断】雷雳直连无丢包、RTT < 1ms；WebRTC 的 jitter buffer、拥塞控制与 pacing 反而增加延迟，libwebrtc 在 macOS 原生构建成本也高。传输用 bridge 上的 TCP（`TCP_NODELAY`）或 UDP/QUIC + 简单分帧即可。
13. **无头运行依赖已登录的 GUI 会话。**【事实】ScreenCaptureKit 与 CGEvent 都需要 Aqua 会话；被控端重启后若停在 FileVault 预启动界面，整条链路不可用。参考做法是关闭 FileVault 并开启自动登录，或通过 SSH 远程解锁 FileVault（macOS 26+ 支持情况【未经核实】）。关闭 FileVault 会带来物理访问风险，必须配合可信物理环境、固件密码与物理锁。
14. **关键 API 全部是 Apple 框架。**【事实】ScreenCaptureKit、VideoToolbox、`CGVirtualDisplay`（私有 Objective-C）、CGEvent；实现语言为 Swift，私有 API 用 bridging header 声明。

## 7. 验收指标

| 维度 | 硬指标 | 备注 |
|---|---|---|
| 有效分辨率 | 3008×1692 HiDPI，像素等价 | 被控端必须暴露该缩放模式；仅全屏模式要求 1:1 上屏，窗口化接受缩放；用同页面并排截图 + SSIM/PSNR 验收 |
| 帧率 | 60fps | 文档、终端、视频三类场景都不掉帧 |
| 端到端延迟 | 输入到上屏 < 33ms；< 16ms 为加分项 | 先用本地直连的 glass-to-glass 延迟作为基准 |
| 音频 | 完全分开：两端互不回传，麦克风不交叉占用 | 硬性否决项 |
| 控制方向 | 固定主控端 → 被控端；单写者；无回环 | 服务端拒绝第二个输入源 |
| 稳定性 | 连续 8 小时无断连、无累积延迟 | 包含睡眠唤醒与网络切换 |
| 成本 | 现成方案必须免费；自研按 M0–M3 里程碑门控 | 6 周做一次评审，不自动冻结 |
| 维护 | 不因 macOS 小版本升级频繁失效 | TCC 权限、私有 API 是主要风险源 |

### 延迟预算估算【推断】

| 段 | 估算 |
|---|---|
| 采集等待 | 0–16.7ms，平均约 8ms（60Hz）；虚拟屏若支持 120Hz 可减半（需实测） |
| 编码（4K HEVC 低延迟） | 4–8ms |
| 网络 | < 1ms |
| 解码 | 3–5ms |
| 上屏 vsync | 平均约 8ms |
| 面板响应 | 约 5ms（VA 面板灰阶响应可能 10–20ms，上表为乐观估计） |
| **合计** | **约 25–35ms**：P95 < 33ms 可达但余量很紧 |

> 先测主控端本地直连同一显示器的 glass-to-glass 延迟，作为远程链路的基准；< 33ms 是绝对指标，不是相对本地的增量。

## 8. 方案空间

| 路径 | 方案 | 优势 | 短板 | 状态 |
|---|---|---|---|---|
| A | Sunshine + Moonlight / 系统屏幕共享 | 免费、开源或系统自带，可离线局域网直连 | 客户端 HiDPI 二次重采样；高性能模式分辨率上限与音频回传 | 已排除 |
| A′ | RustDesk（AGPL，可直连 IP，H.265 走 VideoToolbox；不使用付费 Server Pro） | 免费、开源、离线可用 | 客户端 Retina 缩放大概率同属二次重采样【推断】 | 2026-10-22 决定不测：日常使用过，不能解决问题 |
| B | Deskflow + AirPlay / 系统屏幕共享 | 键鼠单 server，天然消灭控制环 | Deskflow 按屏幕边缘切换，而远程画面只是主控端上的窗口，坐标无法对应；AirPlay 面向视频非交互 | 结构性不成立【推断】 |
| C | 自研薄层：`CGVirtualDisplay` + ScreenCaptureKit + VideoToolbox + TCP/UDP over bridge + CGEvent | 可做到像素等价、音频不进链路、单输入源 | 周级成本，TCC/私有 API 维护税 | 主路径 |

> 自研不写 VNC，不碰 Apple 私有屏幕共享协议，不引入 WebRTC。传输用 bridge 上的 TCP（`TCP_NODELAY`）或 UDP/QUIC，编解码用 VideoToolbox，输入注入用 CGEvent。Parsec、Jump Desktop 依赖账号或付费，不进入候选。

## 9. 决策与里程碑

### 当前判断

- 工作负载是编码/终端/浏览器，33ms 足够；< 16ms 是加分项。决定体验的是客户端 1:1 呈现与输入体感，而不是视频层的带宽或帧率上限。
- 现成方案池已基本穷尽：A 已排除，B 结构性不成立，仅剩 A′ 值得限时排除。
- 显示层是否决项：`vdscreen` 基于 `CGVirtualDisplay`，支持自定义逻辑尺寸 + 2× HiDPI，由 launchd 托管；若开源实现复验失败，自研虚拟显示（参考 `vdscreen` / `DeskPad`，均为 MIT），仍不成立才降级 4K 原生。
- 主路径为 C：显示层用 `vdscreen`（或内置同等 `CGVirtualDisplay` 逻辑），视频/输入/传输自研。

### M0：前置验证（1–2 天）

1. `vdscreen on 3008x1692`：确认 HiDPI 生效、60Hz、睡眠唤醒/重启/登出后自动恢复；打印 `CGDisplayCopyDisplayMode` 的 pixel width/height 与 ScreenCaptureKit 实际捕获尺寸（3840×2160 还是 6016×3384）——这决定 α′/β。
2. 显示器链路探针：确认 4K60 的实际色度（4:4:4 / 4:2:0）与位深，作为像素等价的本地基准。
3. 确认 GUI 会话自动恢复方案，并评估自动登录的物理安全边界。
4. 救援通道：重启后、登录前的 VNC 可用性；不可用则先解决预登录救援。
5. 网络：测 bridge 的实际吞吐与 RTT 基线。
6. A′ 限时半天：RustDesk 直连 IP（不使用付费 Server Pro），记录有效分辨率、实测延迟、音频去向、清晰度。

退出条件：A′ 全部达标 → 停止自研，固化配置；虚拟屏稳定且捕获面确认 → 进入 M1。

### M1：视觉等价 spike（不接输入）

- ScreenCaptureKit → VideoToolbox HEVC 低延迟 → TCP → VideoToolbox 解码 → Metal 上屏；
- 与本地同页面并排截图 diff，慢动作视频测 glass-to-glass 延迟；
- 决策：α′ 还是 β；4:2:0 还是 4:4:4；
- 退出条件：捕获面尺寸确认；静态测试图 SSIM > 0.98；glass-to-glass P95 < 33ms；色度采样实测定档。

### M2：输入

- 主控端全屏时以 CGEventTap 截获系统快捷键（⌘Tab、⌘Space、⌃↑ 等），被控端 CGEvent 注入；
- 覆盖修饰键映射、连续滚动（带 phase）；Secure Input 输入框、触控板手势为已知限制。

### M3：加固

- 加固护栏全部落地，连续 8 小时稳定。

### 自研分层

- 显示：`CGVirtualDisplay`（`vdscreen` 或内置）；
- 采集：ScreenCaptureKit；
- 编码：VideoToolbox（HEVC 优先，低延迟码控）；
- 传输：TCP（`TCP_NODELAY`）或 UDP/QUIC over Thunderbolt Bridge；
- 呈现：Metal，1:1 上屏（α′ 或 β）；
- 输入：CGEventTap（主控端）+ CGEvent（被控端）；
- 音频：不采集、不传输；被控端声音由被控端本机输出；
- 权限：屏幕录制、辅助功能、输入监控三类 TCC 权限与采集/注入逻辑解耦。

### 加固护栏

- **虚拟显示看门狗**：launchd 常驻 + 健康检查；显示丢失自动重建并告警。
- **延迟预算**：采集 ≤ 8ms、编码 ≤ 6ms、网络 ≤ 1ms、解码 ≤ 6ms、渲染 ≤ 8ms；任一段超限记录并降级。
- **音频隔离**：默认传输链路不含音频字节（`--audio` 显式开启才传）；主控端不出现被控端音频设备，不切换系统默认输出、不占用麦克风。
- **单写者**：主控端不运行被控端，被控端不接本地键鼠，客户端是唯一输入源；服务端拒绝第二个输入源。
- **权限医生**：macOS 升级后检查屏幕录制/辅助功能/输入监控，给出一次性重授权引导。
- **救援通道**：保留系统屏幕共享（VNC），用于处理 TCC 弹窗与 GUI 故障；自动化与服务的带外管理走 SSH。
- **安全**：雷雳直连使用配对密钥；不监听对外接口；无遥测。

### 量化倒戈阈值

1. 无头虚拟显示连续 7 天内重建或丢失 ≥ 3 次，或单次稳定运行 < 4 小时 → 放弃 `vdscreen`，转自研虚拟显示或 4K 降级。
2. 端到端延迟连续 14 天 P95 > 33ms 或 P99 > 50ms，且调优无改善 → 重审采集/编码/上屏各段，评估 120Hz 虚拟屏与编码参数。
3. 音频隔离任一次失败（被控端声音出现在主控端、默认输出被切换或麦克风被占用）→ 定位并移除引入音频的组件。
4. 30 天内发生 ≥ 2 次控制环或双写 → 引入单写者令牌 + 心跳 + 超时 + 可见指示。
5. macOS 小版本升级后 48 小时内无法恢复 → 重新评估私有 API 依赖，考虑 4K 原生或物理方案。
6. 自研 6 周做一次评审：未达到 MVP（3008×1692 像素等价 + 60fps + < 33ms + 音频隔离 + 单输入源）→ 评估缩范围、继续或回退，不自动冻结。

## 10. 约束

1. **客户端屏幕**：主控端外接 4K 显示器，在其上远程操作被控端；不采用物理切换显示器的方案。
2. **分辨率**：3008×1692 HiDPI 是硬需求，不接受降级到 4K 原生或 1080p HiDPI。
3. **音频**：完全分开——两端音频互不回传，麦克风也不交叉占用。被控端声音由被控端本机输出，不进入传输通道。前提是被控端在可听范围内；若不在，需要独立音频通道，但不得经过主控端默认输出。
4. **传输**：雷雳 5 是硬要求；不把公网或无线作为主路径。
5. **项目性质**：先作为个人工具跑通；条件成熟时开源产品化，但产品化不反向绑架当前设计。
6. **现成工具门槛**：必须完全免费（不依赖付费或专业版），运行时无需外网、账号或云服务。
7. **工作负载**：编码/终端/浏览器为主；视频、设计、游戏不是主场景。
8. **音频语义**：需要听被控端的声音，但不能劫持主控端；不切换主控端系统默认输出、不占用麦克风。
9. **会话形态**：窗口化与全屏都要支持。
10. **自研节奏**：业余时间，无交付期限；按 M0–M3 里程碑门控，6 周做一次评审，不自动冻结。
11. **无头状态**：按始终无显示器处理。
12. **硬件约束**：参考部署只用现有设备，不引入新硬件。
13. **输入源唯一**：被控端始终不接本地键鼠，只由主控端控制。
14. **实现语言**：Swift。
15. **开源产品化边界**：定义为可复现的 GitHub 仓库 + 构建说明，不以 App Store 分发为目标；私有 API 与 TCC 使商店分发不现实。
16. **控制面分离**：自动化任务由 SSH/launchd 管理；GUI 通道只是人工桌面通道，其故障不得影响自动化任务的运行与恢复。

## 11. 风险

- **过度自研**：写完后发现现成工具已满足 90%，且自研版在系统升级后持续返工。
- **产品化反噬**：过早抽象通用能力，拖慢个人工具闭环；先满足单机场景，再决定开源边界。
- **客户端二次重采样**：只验收被控端分辨率、不验收全屏 1:1 上屏，结果与 Moonlight 同样发糊。
- **色度采样**：4:2:0 导致彩色文字边缘发虚，验收需包含终端彩色输出与浏览器小字号。
- **音频漏洞**：验收时只测画面不测音频，交付后才发现声音仍在主控端。
- **控制环复发**：主控端误开被控端服务；服务端未拒绝第二个输入源。
- **输入注入受限**：安全输入框、触控板手势、修饰键映射可能无法完整转发。
- **权限与私有 API**：TCC 权限重置、虚拟显示私有 API 变更，导致每次 macOS 升级都要修。
- **TCC 弹窗死锁**：录屏权限重新确认的弹窗出现在无头被控端上，需要画面才能点、点了才有画面；依赖 VNC 救援通道解锁。
- **GUI 会话缺失**：重启后停在 FileVault 预启动界面，采集与注入全部失效。
- **自动登录的安全让步**：关闭 FileVault + 自动登录意味着物理接触即完全控制；必须配合可信物理环境、固件密码与物理锁。
- **EDID 依赖**：换线、换转接器、换显示器后分辨率能力回退。
- **免费工具的无头支持未验证**：RustDesk 可能依赖物理显示或已登录的图形会话。
- **自研前置被忽略**：没有 3008×1692 的虚拟显示，采集、编码、传输都无从谈起。
- **热门逆向项目 ≠ 适用**：`sammcj/force-hidpi`（18★）依赖物理 4K 显示器，`KhaosT/CGVirtualDisplay`（40★）只是示例；真正支持无头的 `vdscreen` / `vdisplay` 仍是 0★ 小项目（MIT），成熟度低；`Stengo/DeskPad`（约 7.9k★，MIT）可作虚拟显示参考实现。
- **免费/离线过滤后工具池过窄**：排除付费与云服务后，现成方案已基本穷尽，自研是主路径。
- **本地延迟基准未测**：不知道主控端本地驱动同一显示器的 glass-to-glass 延迟，33ms 目标可能没有余量。
- **音频输出不可听**：被控端的现有扬声器或 3.5mm 若不在可听范围，“不新增硬件”与“需要听声音”冲突。
- **产品分发受限**：私有 API 与 TCC 使 App Store 分发不现实，开源产品只能走源码构建/自签，用户门槛高。
- **KVM 单点化**：把自动化控制也绑在 GUI 链路上，导致 GUI 故障拖垮常驻任务；自动化必须走独立 SSH/launchd 通道。
