# BoltKVM 项目设计文档

> 状态：M0 显示层、M1、M2、M3 与应用化均已落地并完成实测（2026-10-26）。解码链路 P95 25.4–27.0 ms，GUI 采集→上屏 P95 33.2 ms，8 小时连续运行 0 断连，重启自动恢复已验证。M0 整体尚未关闭——真无头拔线复测、睡眠/唤醒、音频可听性与物理延迟基准仍开放，详见 [M0 报告结论](../reports/2026-10-21-m0-display.md#9-结论) 与 [未完成事项](../plans/open-items.md)。

## 1. 目标

在两台 macOS 设备之间，以接近本地直连的清晰度与低延迟操作对端完整桌面（被控端可为无显示器的无头 Mac）：

- **默认显示模式**：3008×1692 HiDPI @ 60Hz（背板像素 6016×3384，支持在设置中切换或自定义分辨率）；
- **延迟目标（SLO）**：解码链路（采集→解码）P95 < 33 ms；GUI 呈现（采集→上屏，不含输入反向上行）P95 < 50 ms；
- **音频隔离**：默认不采集、不传输音频，被控端声音由本机输出，不劫持主控端系统输出设备；仅在显式开启时转发音频；
- **单向控制**：控制方向固定为主控端 → 被控端，从拓扑上消除双向互控死循环；
- **直连优先**：优先使用雷雳网桥（Thunderbolt Bridge）点对点直连，不依赖公网、中继或外部账号。

核心体验指标是**像素等价**：被控端桌面在主控端上的文字与边缘清晰度，与本地直接以 HiDPI 驱动显示器一致。

## 2. 非目标

- 不做跨公网远程桌面或云端中继；
- 不做双向互控；
- 不采用物理 KVM 切换器切换显示器输入源（主控端显示器始终由主控端驱动）；
- 不支持 App Store 分发（依赖私有虚拟显示 API 与本地监听端口）。

## 3. 参考测试环境

文中的实测数据均采集自以下参考环境（工具本身适用于任意搭载 Apple Silicon、运行 macOS 15+ 的 Mac）：

| 项目 | 参考配置 |
|---|---|
| 被控端 | Apple M4 Pro Mac mini，无头运行 |
| 主控端 | Apple M5 Pro MacBook Pro，外接 32 英寸 4K（3840×2160）@ 60Hz 显示器 |
| 物理连接 | 雷雳 5 线直连（Thunderbolt Bridge，双向 80 Gbps 标称链路，TCP 实测约 60 Gbps） |
| 默认显示模式 | 逻辑 3008×1692 @ 60Hz，HiDPI 背板 6016×3384 |
| 网络配置 | 独立雷雳网桥子网，不经过局域网路由器或公网 |

## 4. 典型场景

- 被控端长期在线，承担常驻自动化任务与编译开发工作；
- 主控端为移动笔记本，按需接入并操作被控端完整 GUI 桌面；
- 自动化管理面（SSH / launchd）与远程桌面通道相互独立，GUI 通道启停或故障不影响后台任务运行。

## 5. 现有方案评估

### 5.1 macOS 系统自带屏幕共享

- 标准模式基于 VNC/RFB，帧率与画质受限；
- 高性能模式分辨率上限为 4K / 1080p HiDPI，不支持 3008×1692 HiDPI（背板 6016×3384），且强制回传音频；
- 原生支持锁屏解锁与系统级权限弹窗交互；
- **结论**：不作为日常主方案，保留为系统级 VNC 救援与锁屏解锁通道。

### 5.2 Sunshine / Moonlight

- macOS 宿主端成熟度较低，键鼠映射不符合 macOS 习惯；
- 客户端在 HiDPI 缩放模式下存在二次重采样导致文字发糊（`moonlight-qt #1185`）；
- **结论**：排除。

### 5.3 显卡欺骗器（Dummy Plug）与虚拟显示

- 普通 HDMI 欺骗器受限于固定 EDID，往往只能提供 LoDPI 的 3008×1692 或标准 4K；
- 无头场景下，通过 `CGVirtualDisplay` 创建软件虚拟屏可直接暴露 `3008×1692 @ 60Hz HiDPI`（背板 `6016×3384`），无需外接硬件欺骗器；
- ScreenCaptureKit 只能采集已存在的显示器，因此内建虚拟显示是无头被控端的前置基础。

### 5.4 Deskflow / RustDesk / 商业远控

- Deskflow 仅共享键鼠、不传输画面，且基于屏幕边缘切换，不适用于窗口化远控；
- RustDesk 客户端在 Retina 缩放下同样存在重采样模糊问题；
- Parsec、Jump Desktop 等商业工具依赖外部账号或付费订阅，不符合离线自治约束。

## 6. 技术事实与边界

以下结论区分 **【事实】**（已实测或有明确技术依据）与 **【推断】**：

1. **雷雳网桥带宽余量充足。【事实】** 雷雳网桥裸 TCP 双向吞吐实测达 60–64 Gbps（RTT < 1 ms）。即使采用 600–1400 Mbps 的 ProRes 422 码流，网络占比也不足 3%，端到端延迟完全取决于采集、编解码与渲染合成。
2. **ScreenCaptureKit 支持原生背板像素采集。【事实】** 针对 3008×1692 HiDPI 虚拟屏，按 `CGDisplayMode` 的像素宽高（6016×3384）配置 `SCStreamConfiguration`，可直接抓出 6016×3384 原生清晰图像。
3. **像素等价的两种传输路径。【事实】**
   - **α′（4K 缩放 + 全屏切 1× 模式）**：采集端缩放到 3840×2160，客户端全屏时将物理 4K 屏切为 1× 原生模式 1:1 显示；对应服务端「标准」画质档位及 CLI `--switch-mode`。
   - **β（2× 背板原画传输）**：直接采集并编码 6016×3384 像素（ProRes 422），由主控端合成器完成与本地一致的缩放，窗口化与全屏均清晰且无需切换显示器模式；对应服务端默认的「清晰」画质档位。
4. **ProRes 422 编码延迟显著低于 HEVC。【事实】** 在 Apple Silicon 硬件编码器上，4K HEVC 的管线延迟约 22 ms（6K 下更无法达到 60 fps）；而 ProRes 422 在 4K 下编码延迟约 9 ms，在 6K（6016×3384）下约 12.5 ms 且能稳定满帧 60 fps（见 [ADR-0003](../adr/0003-prores-422-primary.md)）。
5. **点对点直连无需 WebRTC。【事实】** 雷雳网桥无乱序且 RTT < 1 ms，采用裸 TCP（`TCP_NODELAY`）配简单的帧头与发送队列丢帧控制即可实现最低延迟，省去 WebRTC 的抖动缓冲与复杂构建依赖。
6. **无头采集依赖已登录的 Aqua 图形会话。【事实】** ScreenCaptureKit 与 CGEvent 均需在已登录桌面会话中运行。被控端需关闭 FileVault 并开启自动登录（配合可信物理环境），若停留在锁屏界面则通过系统 VNC 救援解锁。
7. **GUI 进程直接创建虚拟屏不稳定，需由子进程持有。【事实】** 同一份 `CGVirtualDisplay` 代码在 CLI 进程中稳定创建 HiDPI 虚拟屏，但在 GUI 应用主进程或开启 Hardened Runtime 时会被拒绝或退化为 LoDPI。因此 `BoltKVM.app` 采用主进程管 UI、子进程 `boltkvm-server` 持有虚拟屏与采集管线的架构，TCC 权限按责任进程自动继承。

## 8. 系统分层与加固机制

### 8.1 核心分层

- **虚拟显示**：`Sources/CVirtualDisplay`（封装自开源 `vdscreen` 的 MIT 核心代码），由 `boltkvm-server` 子进程创建并持有；
- **屏幕与音频采集**：ScreenCaptureKit（`Server.swift`），按 `displayID` 精确锁定目标屏，持有 `PreventUserIdleDisplaySleep` 防止无头显示器休眠冻屏；
- **视频编解码**：VideoToolbox 硬件加速，默认 ProRes 422，可选 HEVC；解码端限制在途帧上限（2 帧）防止积压；ProRes 一律按 10-bit 4:2:2 解码（标准模式也不降到 8-bit）。**色彩模式**分「标准」（采集 8-bit 4:2:0 BT.709）与「广色域」（采集 10-bit 4:2:2 Display P3），随 `config` 包按主机下发；虚拟屏的帧缓冲本身是 sRGB，所以广色域只在 `--display-id` 直接采集物理 P3 显示器时带来真实色域收益；
- **传输与加密**：TCP（`TCP_NODELAY`、`SO_SNDTIMEO` 2s 发送超时 + 4 帧/8 MB 发送队列上限防止慢客户端反压堆积）；PSK + HMAC-SHA256 挑战应答认证，X25519 临时密钥交换 + ChaCha20-Poly1305 会话加密；
- **画面渲染**：Metal（`MTKView`），4 顶点 Triangle Strip 等比缩放渲染，默认开启 `displaySyncEnabled` 并由解码回调直接泵送 `view.draw()`；
- **输入捕获与注入**：App 主控端使用窗口内 `NSEvent` 本地监听（免输入监控 TCC，移出画面或失焦自动释放按键）；CLI 主控端使用 `CGEventTap`；被控端使用 `CGEvent` 注入并实时对齐修饰键掩码，系统级操作（调度中心、显示桌面）通过 `CoreDockSendNotification` 命令通道执行（桌面切换用带 1/0 参数的 `showdesktop.set`，旧 Dock 回退到 `showdesktop.awake`）；键鼠发送走独立串行队列，队列上限 64，拥塞时丢弃过时事件而不阻塞主线程；
- **连接管理与重连**：主控端维护多主机列表，按主机保存地址、端口、分辨率、键鼠/音频开关与色彩模式；会话中断后自动重连（0.5–5 秒退避并显示重连次数），错误密码仍直接失败。

### 8.2 运行护栏

- **防休眠与自愈**：服务端常驻持有防显示器休眠断言，虚拟屏被系统移除时子进程退出（退出码 3），由宿主 App 在 3 秒后自动重启重建；
- **单实例锁**：基于 `flock` 的进程锁（`app.pid` 与 `server.pid`），防止多实例争抢端口或创建多块虚拟屏拖垮帧率；
- **延迟与丢帧监控**：服务端每 2 秒输出统计（编码均值 > 12 ms 或丢帧率 > 1% 告警），客户端每 60 秒输出窗口统计（解码 P95 > 33 ms 或 GUI P95 > 50 ms 告警）；
- **带外救援通道**：保留 SSH 与系统屏幕共享（VNC），可用 `scripts/rescue.sh` 随时核验连通性。
