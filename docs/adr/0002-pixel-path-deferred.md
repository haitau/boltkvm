# ADR 0002：像素路径选择 α′（全屏切 4K 原生）

- 状态：已接受（α′；2026-10-21 M1 编码探针后）
- 日期：2026-10-21

## 背景

客户端 3008×1692 HiDPI 的帧缓冲是 6016×3384，再缩放到 3840×2160 面板。若直接接收 4K 帧，客户端会先放大到 6016×3384、再缩回 3840×2160，产生二次重采样（moonlight-qt #1185）。实现像素等价有两条路：

- **α′ 全屏切原生**：被控端采集 3840×2160；主控端全屏时把显示器临时切到 1x 3840×2160，帧 1:1 上屏；退出恢复。
- **β 传 backing 尺寸**：传输 6016×3384，客户端按 backing 像素 1:1 绘制，由合成器执行与本地相同的缩放；窗口/全屏均等价。

## M0 实测输入（2026-10-21）

- 虚拟显示：逻辑 `3008×1692`，背板 `6016×3384`，60Hz；
- ScreenCaptureKit 的 `SCDisplay` 返回 points 尺寸 `3008×1692`，按 `CGDisplayMode` 的 `6016×3384` 配置后，抓帧得到原生 `6016×3384`（见 [M0 显示层报告](../reports/2026-10-21-m0-display.md)）；
- 因此 β 的捕获面已经具备；α′ 需要在采集端额外缩放到 3840×2160，并承担客户端模式切换。

## M1 编码探针（2026-10-21）

【事实】在 M4 Pro 上用 VideoToolbox HEVC 低延迟硬编实测：

- 6K（6016×3384）真实桌面：编码平均延迟 **162.89ms**、吞吐 23fps、515/870 帧丢弃；
- 4K（3840×2160，SCK 从 6K 缩放）：0 丢帧、编码平均延迟 **18.67ms**、吞吐 52fps。

结论：β 的 6K60 编码在当前硬件/编码器上不成立；α′ 的 4K60 可行。详见 [M1 编码探针报告](../reports/2026-10-21-m1-encoder-probe.md)。

## 决策

M0/M1 实测后，最终选择：

- **α′ 为 M1 主路径**：被控端采集 6K 背板、缩放到 4K、HEVC 4K60 编码；主控端全屏时切到 1× 3840×2160，4K 帧 1:1 上屏；退出恢复。
- β 不再作为 M1 目标；仅在未来编码器能稳定 6K60 且延迟达标时重评。
- 若 α′ 的 SCK 缩放画质不达 SSIM 阈值，再回头评估 6K 编码或 4K 原生 UI。

## 后果

- 客户端全屏时需要把显示器切到 1× 3840×2160，退出时恢复；模式切换的黑屏时间需实测；
- 被控端由 SCK 执行 6K→4K 缩放，必须用 SSIM/PSNR 验证它与本地 WindowServer 缩放是否等价；
- 像素等价验收只在全屏模式要求 1:1，窗口化接受缩放；
- β 的 6K 管线不进入 M1，相关抓帧能力保留作 M0 证据与后续评估。
