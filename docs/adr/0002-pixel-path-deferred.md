# ADR 0002：像素等价路径（α′ 4K 缩放与 β 原画传输）

- 状态：已接受（M1 落地 α′；应用化阶段在 ProRes 422 下同时支持 β 并设为默认）
- 日期：2026-10-21（2026-10-22 更新）

## 背景

被控端 3008×1692 HiDPI 虚拟屏的真实背板像素为 `6016×3384`。若服务端将画面缩放到 4K（3840×2160）传输，而主控端又运行在 3008×1692 HiDPI（6016×3384 背板）下，客户端渲染时会发生 `6016 → 3840 → 6016 → 3840` 的多次重采样，导致文字发糊。

消除重采样发糊有两条路径：

- **α′（4K 采集 + 客户端全屏切 1× 4K 模式）**：被控端采集缩放到 3840×2160；主控端全屏时将物理 4K 显示器临时切到原生 1× `3840×2160` 模式，使 4K 帧 1:1 上屏，退出全屏时恢复原显示模式。
- **β（6K 背板像素原画传输）**：服务端直接按虚拟屏真实像素 `6016×3384` 采集并编码，客户端按真实像素解码后交由 Metal 渲染，无论窗口化还是全屏均无需切换物理显示器模式。

## 实测演进

### 1. M1 阶段（HEVC 编码器，2026-10-21）

在 M4 Pro 上使用 VideoToolbox HEVC 硬件编码实测真实桌面（见 [M1 编码探针报告](../reports/2026-10-21-m1-encoder-probe.md)）：

- `6016×3384`（6K）：平均编码延迟 **162.89 ms**，吞吐仅 **23 fps**，大量丢帧；
- `3840×2160`（4K）：0 丢帧，平均编码延迟 **18.67 ms**，吞吐达标。

由于 HEVC 硬件编码无法支撑 6K60，M1 阶段选择 **α′** 作为主路径（CLI `--width 3840 --height 2160` 配合客户端 `--switch-mode`）。

### 2. 应用化阶段（ProRes 422 编码器，2026-10-22）

在 [ADR-0003](0003-prores-422-primary.md) 将默认编码器切换为 **ProRes 422** 后，硬件编码器在 `6016×3384` 分辨率下实测可稳定达到 **60.0 fps**（编码延迟约 12.2–12.5 ms，码率约 1.1–1.4 Gbps，占雷雳桥带宽约 2%）。

这使得 **β 路径** 在雷雳网桥上完全成立，且免去了客户端切换显示器模式的黑屏等待，窗口化与全屏下文字均清晰锐利。

## 决策

系统同时保留两条路径，按被控端「画面质量」档位切换：

1. **清晰（`pixel`，App 默认值，即 β 路径）**：按虚拟屏 2× 真实像素（如 `6016×3384`，宽度上限 8192）采集并编码，适合雷雳网桥直连；
2. **标准（`standard`，即 α′ 路径）**：将采集宽度限制在 3840 以内，适合慢速链路或低带宽场景；CLI 下仍可通过 `--switch-mode` 启用全屏 1× 4K 模式切换。
