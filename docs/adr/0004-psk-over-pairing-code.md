# ADR 0004：认证继续用预共享口令，不做配对码换密钥

- 状态：已接受（2026-10-23 评估，暂不实现 A 方案）
- 日期：2026-10-23
- 相关：[README 连接密码](../../README.md)、[连接管理器设计](../plans/2026-10-22-connection-manager-design.md)

## 背景

现在两台机器靠**同一个 8 位连接密码**互相认证：服务端发 32 字节随机数，客户端回
`HMAC-SHA256(PBKDF2(password), nonce)`，对不上就断开。密码在被控端首次启动时生成、
显示在面板里，主控端手动填一次，按台存进 `~/Library/Application Support/BoltKVM/keys/`。

备选方案 A：被控端显示一个**短命配对码**（几分钟有效），主控端输入配对码后，双方在加密通道里
交换一把 256 位随机密钥，之后用那把密钥认证，配对码作废。听上去更"正规"，也能随时吊销设备。

问题是：值不值得为它改协议、加状态机、改界面。

## 决策

**不做 A。** 认证保持预共享口令，把精力放在别处。

## 理由

1. **离线爆破已经被 PBKDF2 挡住。** 8 位口令约 40 位熵，但生成后会先经
   PBKDF2-SHA256（12 万次）拉伸再当密钥，一次猜测约 25–30 ms。抓走一次握手后离线爆破：
   单卡 2⁴⁰ × 30 ms ≈ 1000 年，一千张卡的集群 ≈ 1 年。这个威胁模型是"有人能接到你的
   雷雳线上"，不是公网；在这个前提下 40 位 + 拉伸够用。
2. **在线爆破不可能。** 认证失败后服务端停 1 秒，40 位需要上万年。
3. **A 的简单实现比现在还弱。** 最省事的做法是"配对码当 PSK，在通道里把随机密钥传过去"——
   可一旦有人录下这次握手，6–8 位配对码可以离线爆破（20–40 位、无拉伸），拿到随机密钥后
   长期有效。要做对就必须上 PAKE（SPAKE2 / OPAQUE），而 CryptoKit 不提供，手写 PAKE
   是典型的"不该自己写"的密码学。换句话说，A 的真实成本不是"加个界面"，是"引入一个
   需要审计的密码协议"。
4. **A 不解决真正缺的东西。** 它换来的是一把更长的静态密钥，但**静态密钥 + 录制的流量
   仍然可以解密**——缺的是前向保密，而前向保密要在每会话做临时密钥交换（X25519 ECDH），
   跟"配对码"是两件独立的事。真要提高安全上限，应该先做 X25519，而不是先做配对码界面。
5. **A 把一次简单操作变成一次有时限的操作。** 配对码会过期，主控端不在手边就得重新生成；
   而现在密码是持久的，抄一次就行。
6. **成本不对称。** A 要动握手协议（新增模式字节 + 状态）、服务端与客户端两套代码、
   面板与编辑器 UI、以及一整套"配对失败/过期/重放"的测试；收益是"口令更长"和"能吊销单台"，
   而后者用现在的「重新生成密码」也能做到（代价是所有设备重填）。

## 什么情况下要重新评估

- 端口暴露到不受信任的网络（`--bind 0.0.0.0` 常态化，或跨公网）——那时 40 位不够，且需要
  前向保密；
- 需要给多台主控端发不同密钥、单独吊销某一台；
- 想在主控端完全不落盘任何秘密（现在密码按台存在本机 0600 文件里）。

一旦触发，顺序是：

1. 先做**每会话 X25519 临时密钥交换**（前向保密：握手包被录下来也解不开流量）；
2. 再把静态密钥升级到 256 位随机（这一步才是"配对码/二维码"真正想解决的问题）；
3. 如果要做配对，必须用 PAKE，不允许"短码当 PSK 传密钥"的简化。

也就是说，配对码是第 3 步，不是第 1 步。现在跳到最后一步做，收益最小、风险最大。

## 后果

- 口令必须靠带外方式传递（看屏幕、复制、口述），这是已知且接受的摩擦；
- 没有前向保密，`--insecure` 仍是明文逃生口（会打警告）；
- 重新生成密码 = 所有主控端重新填一次，没有"逐台吊销"。
